# Integrating job status and step claims

Status: design only. The live pipeline still uses eventually consistent KV, and the isolated coordinator prototype is not an authority for jobs or final writes. The tests in `test/job-concurrency.test.ts` characterize three current races: duplicate model calls, duplicate finalization, and a late first attempt overwriting a completed second attempt.

## Scope and state

The coordinator needs an authoritative job record keyed by job ID, a real-run generation, one record per mailbox, and one finalization record. A mailbox record stores its alias and linked-account identity/version, state (`todo`, `running`, `done`, `failed`), attempt number, unguessable attempt token, start/deadline, and an immutable accepted-partial reference when done. The finalization record similarly has its own token and generation. Job and row status exposed to the UI must come from this state, not from KV projections or a page's previously read marks. Store only masked mail in accepted partials; never log payloads or tokens.

A real-run singleton owns active real jobs and their authority; test jobs need separate isolated state and must not publish real cursor, cache, history, recheck, last-run, or job state. A test's existing `checked` write must also be identity-fenced, or omitted until that behavior is migrated safely. The immutable state retention and cleanup policy must be separate from the prototype's synthetic 24-hour TTL.

## Changes by file

1. `src/run-coordinator.ts`: introduce atomic, idempotent create/get job, observe job, claim-next, renew-claim, accept-result, give-up, claim-finalization and finalize operations. Use a transaction for each transition and a job generation in addition to a random attempt token. `claim-next` atomically selects at most one mailbox and writes `running`; observing a job never claims it. A stale attempt can be replaced only after its recorded deadline, not merely because the caller calls itself sequential. Late results, failed mailbox records and finalization requests must match the current job, generation, alias, token and deadline. Stage large partials as bounded immutable chunks before accepting their reference; verify completeness and hash before the transition. A timeout alone does not permit old writers to alter authoritative data.
2. `src/jobs.ts`: `startJob` creates and claims the real job atomically before exposing it; persist fixed options, `previous`, mailbox identities and driver in the authoritative record. Replace `planStep`'s independent KV reads and deferred claim with coordinator observe/claim operations. Return the current row snapshot for `wait`, a token-bound work closure for `process`, and a separately claimed finalization closure for `finish`. Preserve the existing retry shares and `MAX_ATTEMPTS`, but derive them from the authoritative attempt count. `stepMailbox` must collect without publishing KV marks, then submit its staged partial using the same token; on rejection, return stopped or re-observe, never overwrite another attempt. Record a caught error as a failed result only while its token is current. Do not trust the old `marks` snapshot to decide quota or completion; read the accepted generation's status.
3. `src/jobs.ts` finalization: replace `finishJob`'s direct `assemble`, `job-result` and `job-done` writes with a claimed, resumable manifest build and strongly consistent atomic generation publication. It must include all accepted partials, digest, result, job done, cursor, cache, failure, recheck, history and last-run values. Validate account identities and current done/settings versions at publication; retry preparation after a version change. A lost response after success must return the same committed digest/result, and a stale finalizer must be unable to publish. Do not implement this step by checking a token before a sequence of KV writes: the token may expire while writes are in flight.
4. `src/jobs.ts` cron: `runStep` must use the same claim path as a browser. Remove `sequential` as a claim override. `driveJob` must poll authoritative job/step progress and back off on `wait` or bounded transient failures; it cannot infer progress from stale KV. Replace `finishOnly`'s blind overwrites with an atomic explicit give-up transition for unclaimed or expired attempts. It must never turn an active attempt into `not reached` and then finalize behind it. Renewal and expiry use coordinator time, not a browser-supplied timestamp. No network or AI work may occur inside a coordinator transaction.
5. `src/web.ts`: obtain the active job notice and `readResult` from the authoritative store. `observe` and paused/cron watch requests remain read-only and show committed status. One request may receive `process`; another receives `wait`. Keep the existing stream/refresh behavior, but re-observe after work succeeds or loses its token. Keep HMAC, session and CSRF controls; tokens stay inside trusted service bindings, never in URLs, HTML or logs. Update the scheduled-run and browser handlers together so no route bypasses claims.
6. `src/accounts.ts`, `src/digest.ts`, and owner edit routes: represent account link/unlink/relink and done/settings edits with versioned, strongly consistent state or mutations coordinated with finalization. Snapshot and revalidate these versions at commit; never let a result from a previous account identity repopulate its replacement's cursor/history. Refactor digest reads and next-run inputs to resolve the committed generation. KV can remain a non-authoritative projection, with a strong-store fallback on a cache miss or stale version.

## Required tests before wiring real jobs

* Coordinator transaction tests: two simultaneous starts yield one real job; two simultaneous `claim-next` calls yield one claim; duplicate requests with the same token are idempotent; a stale generation or expired attempt cannot stage, fail, renew or finish. A lost claim response can be retried without incrementing attempts. A second attempt's accepted result survives a late first attempt and coordinator restart. Repeat expiry/claim races around the exact deadline.
* Job and route tests: two browser requests, cron plus browser takeover, duplicate internal loopbacks, and `finishOnly` racing a live step. Observe-only and paused requests produce no claims. A dead step retries with shares `[full, 15, 5]`; exhausted attempts become failed once. The page displays authoritative `running`, `done`, `failed`, stopped and committed result even if KV returns stale data.
* Commit tests: two finalizers, stale finalizer after new generation, interrupted preparation and retry at every boundary, lost commit response, missing/duplicate/corrupt fragments, recheck and seen visibility, new done/settings edits and account relink during work. No partial generation may become readable, no cursor may move backwards or skip a failed message, and no accepted data may be silently lost.
* Runtime and rollout tests: measure per-invocation CPU, heap, subrequests, SQLite transaction cost and storage retention using synthetic 500-message jobs in a separate deployment. Verify both cron and browser drivers and crash recovery. Before authority changes, quiesce old workers and drain in-flight KV writers; validate migration and a rollback that cannot resurrect old writers. A passing isolated claim test is not sufficient to enable production traffic.
