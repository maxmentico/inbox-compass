# Run coordination: implementation constraints

Status: **in progress; the existing run path still uses the KV lock.** A lease by itself does not prevent a stalled worker from writing after its lease expires. Do not deploy an isolated lease service as a complete concurrency fix.

## Correctness boundary

One SQLite-backed Durable Object must own real-run generations, active job and step claims, accepted partials, finalization, and the authoritative committed run state. A claim has an unpredictable attempt token and a generation; a later attempt invalidates earlier tokens. A result or commit with a stale token is rejected. Test runs must remain isolated from real-run state.

Gmail and AI work stay in separate Worker requests. They do not run under a Durable Object concurrency gate. Stage results in bounded chunks; only accepted attempts can advance the job. A finalizer prepares immutable, generation-scoped records and publishes a complete manifest using one atomic Durable Object storage operation. A crash before publication leaves the preceding generation authoritative; retry resumes or discards staged records. A crash after publication is treated as success. Old workers cannot write an authoritative cursor, last-run, seen mark or digest after a new generation is published.

The commit must cover digest and run result, last-run, cursor, failure-hold, classifications, history and recheck state together. In particular, an estimate's seen mark cannot become visible without its recheck record. All correctness-critical reads, including the next run's cursor and last-run, must come from the strongly consistent store, not an eventually consistent KV projection. Preserve owner edits such as done marks and settings, and prevent a run using an old mailbox identity from publishing after unlink or relink. Keep the existing privacy rules, redaction, expiry and deletion behavior for any mail content stored in the new system.

## Cloudflare budgets

As documented by Cloudflare on 6 November 2026, Workers Free has 10 ms CPU per invocation, 50 external subrequests and 1,000 internal-service subrequests; Paid has a 30-second default CPU limit and 10,000 subrequests by default. Both plans have six simultaneous outgoing connections. SQLite Durable Objects are supported on Free, and individual SQLite rows and values have size limits. These limits must be measured in the actual runtime and checked again before release, not inferred from local timing. Sources: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/).

* Keep each mailbox in a separate invocation. Avoid one coordinator call per email: use bounded bulk operations and chunk large values, with a budget for existing Gmail, KV, AI and service-binding calls.
* A coordinator operation should perform short storage work. Never hold `blockConcurrencyWhile` over Gmail, AI, KV, or other network I/O: it blocks the object and times out after 30 seconds. See [Durable Object state](https://developers.cloudflare.com/durable-objects/api/state/).
* Limit batch size by encoded bytes as well as count. Verify peak memory, CPU, SQLite row size, storage usage, request count and duration using a 500-email worst case and injected retries. Define headroom below platform limits, and split further when needed.
* Verify the Free and Paid plans separately. Local development does not enforce every deployed limit. Include Durable Object requests, duration and storage in the running-cost comparison.

## Contract for incremental manifest construction

The isolated `buildAssemblyManifest` is a reference planner, not a Free-plan implementation: the opt-in `scripts/benchmark-assembly.ts` measures the cost of serializing a full 500-message manifest. Splitting its returned string into fragments does not bound the cost of constructing it. A digest value alone can contain 500 excerpts of 3,000 characters each, so chunking only between whole key/value writes is insufficient.

Before implementing a resumable producer, provide and test all of the following:

1. The coordinator owns immutable, generation-scoped inputs: accepted partials, the mailbox identities, and one consistent version of every cursor, failure hold, history, run index, done mark and setting needed for the commit. **Never serialize `RunContext.accounts` or an `AccountRecord` into snapshots:** they contain `sealedRefreshToken`. Project only alias, email and the minimal identity/version required to fence relinks. The generic byte snapshot primitive cannot enforce this; its caller must construct and validate the safe DTO before any bytes are staged. Each resume loads the exact input version recorded by the checkpoint. A version label supplied by a caller is not proof that mutable KV contents are unchanged. Reject a missing or changed version and restart from a new snapshot.
2. A resumable serializer walks those inputs without first building the whole manifest, or a whole large digest value, in memory. Limit both encoded output bytes and work per invocation; a limit on operation count alone is insufficient. Deterministic escaping and encoding must preserve the exact value, including Unicode and redacted fields. Persist a checkpoint only after its output fragments are durable.
3. Stage fragments under immutable generation/attempt identifiers, each with a sequence number, byte length and integrity digest. The final manifest identifies the complete ordered fragment set, total byte length and whole-value integrity digest. Retries must be idempotent. Reject missing, duplicated, reordered, corrupted or cross-generation fragments; never interpret a partial value as complete.
4. Publication verifies current generation, attempt, account identities, owner edits and complete staged content, then atomically switches a strongly consistent generation pointer. All readers resolve that pointer and reconstruct values from its verified fragments; they must never observe a mixture of generations. The digest, job result, job done mark, recheck list and seen marks are published together. A coordinator that merely stores opaque chunks or has only a lease does not satisfy this contract.
5. Store expiry as a defined absolute time or otherwise ensure restart/retry does not silently extend retention. Preserve deletion behavior and TTL metadata, including cache arrival metadata. Clean up abandoned fragments and expired generations without deleting data still referenced by a reader. Test privacy redaction before staging; do not put email content in logs.
6. Inject a crash at every checkpoint and publication boundary, replay with a stale token, change the done marks/settings and unlink or relink a mailbox during staging, and verify exact equivalence with the reference planner. Measure CPU and memory on a deployed synthetic Workers environment before connecting this protocol to real jobs.

The current coordinator prototype can store bounded opaque chunks but does not yet implement this source, validation, reconstruction or read protocol. An isolated serializer claiming snapshot consistency on top of the current mutable KV input would therefore be misleading.

Checkpoint identity must include both a unique job-generation scope and the snapshot content ID: identical inputs for separate jobs must not share completion state. The isolated verifier uses a composite key; the synthetic coordinator currently accepts raw content IDs, so these APIs are not wired together. Duplicate start and page requests reject rather than reset progress. After a response is lost, a trusted caller must read the authoritative checkpoint and reconcile its next index before retrying. The backing store must implement atomic create and compare-and-advance and keep checkpoints alive for the required recovery period.

## Rollout and acceptance

1. Exercise overlapping starts, steps and finalizers; stale attempt results; process death before and after commit; restart and replay; stale KV reads; account unlink/relink; and mutable done marks. Confirm exactly one committed generation and no skipped mail.
2. Run synthetic end-to-end tests in the Workers runtime and on a separate Cloudflare test deployment with dummy mail only. Measure the budgets above. Preserve previous digest reading during migration.
3. Quiesce the old deployment and drain in-flight work before switching authority. Old code cannot honor new claims, and KV cache staleness makes merely observing a missing legacy lock insufficient. Define and test recovery and rollback before changing production. A rollback must not allow old code to write over state committed by the new system.
4. Deploy the full path only after those checks pass. An isolated coordinator or passing lease test is not proof that final writes are fenced.

## Production cutover and rollback

Keep production on KV until the following sequence passes on a separate deployment with invented mail, the intended account plan, and no production bindings. Record counts, timings, version IDs and pass/fail outcomes. Keep mail, tokens and raw records out of reports.

1. **Prepare a rollback version before writing a new format.** Provision the SQLite class with an additive deployment at 100% traffic. Keep KV authoritative and deploy a compatibility version that can read both schemas, finish a job at its persisted digest ID, and select authority from a strongly consistent control record. Preserve this version ID. Class lifecycle changes require an atomic deployment, and Cloudflare can refuse a rollback across them. A legacy Worker also rejects new `timestamp-<jobId>-test` IDs and recomputes `timestamp-test` on finalization. Enable the new writer only after the compatibility release serves all traffic. Previously opened browser links keep working against the compatible reader. [Class lifecycle](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/) · [Rollback restrictions](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/rollbacks/)
2. **Close admission and prove old writers have finished.** Gate browser starts, cron, internal steps, finalizers, test jobs, done/settings changes, link/unlink callbacks and index repair/initialization, including writes triggered by reads. Register admitted bridge operations with a durable completion journal. Stop scheduling new runs and drain or explicitly resolve admitted work before import. A scheduled trigger change can take 15 minutes to propagate. A connected streaming HTTP request can run indefinitely. Neither elapsed time nor an absent KV lock proves that an earlier binary stopped writing. If outstanding pre-bridge operations cannot be accounted for, keep the bridge active and defer cutover. [Cron propagation](https://developers.cloudflare.com/workers/configuration/cron-triggers/) · [Request duration](https://developers.cloudflare.com/workers/platform/limits/)
3. **Import and verify behind the barrier.** Copy the covered state server-side into a fresh generation, in bounded pages. Preserve absolute expirations, metadata, old digest IDs and deletion markers. Exclude expired records and credentials. Reconcile key counts and hashes by prefix and mailbox against the authoritative bridge journal, including deletes, owner edits and repeated links of the same email address. Replay accepted bridge changes in sequence and record the verified high-water mark. A single KV listing, two matching cached reads, or waiting one minute is insufficient proof of a complete baseline. Resolve discrepancies before promotion. [KV consistency](https://developers.cloudflare.com/kv/concepts/how-kv-works/)
4. **Switch one authority.** In a single coordinator transaction, verify the expected authority epoch, journal high-water mark, snapshot hash, per-link identity epochs and done/settings revisions, then publish the new head and reopen admission. Readers and writers select the same generation. Give retries a durable operation ID and an explicit outcome. Gate Gmail/notification side effects separately so replaying an ambiguous state commit cannot resend an email. Keep any KV projection asynchronous and generation-tagged.
5. **Rehearse rollback with edits after cutover.** Route to the retained compatibility version and keep the Durable Object authoritative. Cloudflare code rollback does not rewind connected storage. If KV authority must be restored, freeze mutations again, export the current committed state and tombstones, verify the destination against the journal, and use a fresh epoch for reverse cutover. Check that old writers cannot overwrite the exported state. A failed rehearsal blocks production activation. [Code vs. storage rollback](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/rollbacks/)

For the rehearsal, measure the Worker and the SQLite object separately. On Free the ordinary Worker has 10 ms CPU, 50 external and 1,000 internal subrequests per invocation. The SQLite object has a documented 30-second default CPU limit per request, a 1 GB Free per-object limit, an 8 MB SQL row or BLOB limit and 100 bound parameters per SQL statement. Free account quotas include 5 million SQL rows read and 100,000 rows written per day, 100,000 object requests per day and 13,000 GB-s of duration per day. Budget for concurrent staged and committed generations, cleanup, index writes and alarms. Report actual rows read/written and peak retained bytes with a 500-message run, crash/retry and a full retention window. KV also limits writes to a single key to one per second on both plans.
